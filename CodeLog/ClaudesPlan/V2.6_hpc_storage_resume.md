# V2.6 Plan: HPC Storage Protection and Resume-from-Snapshot

## Context

Twenty simultaneous HPC trials wrote results to `/home` (50 GB quota) and filled it, killing all running jobs. The user synced and deleted results from HPC. They need: (1) results redirected to `/groups` (500 GB), (2) disk space guard, (3) rolling snapshot cleanup, (4) staggered starts, and (5) resume-from-snapshot to continue interrupted runs by uploading the last snapshot back to HPC.

## Feature 1: Results to /groups (500 GB)

- `"results_path": "/groups/mcgheealex/results"` in `hpc/Alex.json`
- SLURM template uses absolute `$RESULTS_BASE` from `results_path`
- All sync functions (`_do_sync`, `_wait_and_sync`, `_wait_and_sync_multi`, `sync_results`) accept and use `results_path`

## Feature 2: Disk Space Guard

- `check_disk_space(output_dir)` → `'ok'`/`'warning'`/`'critical'`
  - `< 1 GB` → critical: skip snapshot entirely
  - `< 5 GB` → warning: save snapshot but skip fields
  - `>= 5 GB` → ok: save normally
- SLURM pre-flight: bash `df` check, abort if < 2 GB free

## Feature 3: Rolling Snapshot Cleanup

- `keep_n_snapshots: int = 5` in Params (default: keep first + last 5)
- `cleanup_old_snapshots()` keeps snap_0000 + last N, deletes rest

## Feature 4: Staggered Starts

- `"max_concurrent": 10` in Alex.json (was 200)
- `sleep $(( RANDOM % 30 ))` in SLURM template

## Feature 5: Resume from Last Snapshot

- Bug fix: `save_snapshot_to_disk()` now saves epsilon/d_epsilon
- `find_last_snapshot(run_dir)` → path to last snap_XXXX.npz
- `restore_gs_from_snapshot(snap_path, p)` → full GranuleSystem reconstruction
- `run()` modified: resume branch skips packing, loads state, continues from resume_step+1
- `--resume-from` CLI arg in `run_hpc_headless.py`
- RUN_MODE=4 in `run_all_trials.py`: scans for incomplete trials, uploads snapshots, submits resume SLURM jobs
